    Lesson 1 · What AI is, and why it matters to you

    Big idea: you don't control the brain. You control what it sees. Prompts, system prompts, tools, skills and apps are all ways of changing what it sees.

    1. It continues the "document" it thinks it's in. A chat is one long document. Change the document and you change the prediction. Example: "can you search?" plus a search tool usually leads to it searching.
    2. Its own words steer what comes next. Once it starts "Sure, searching...", it's committed. Make its first words a plan: "Say what you'll do, then wait."
    3. No built-in fact check. Put the facts in front of it (paste them or use a tool) and allow "I don't know."
    4. A dice roll in every word. Regenerate bad answers. Use a lower temperature when it needs to be exact.

    Your insight: words that trigger instant action are bad for a chatbot but right for a worker agent taking orders from another agent (Lesson 10).

    Lesson 4 · Making AI behave

    Big idea: settings decide what's possible. Prompts decide what gets chosen.

    • Three sources of behavior. Training (abliteration weakened its "should I?" reflex), size (an 8B model juggles few rules), and what it sees (tools, prompt, chat, web pages, files, memory).

    • Small-model prompt rules. About 200 words, examples beat rules, and the most important rules go at the start and end.
    • Tools by risk. Never needed: off. Sometimes needed: on per task, guided by the prompt. Can do damage (bash, file writing): off or approval only.
    • Odysseus specifics. Tools toggle one by one. Persistent memory feeds into context, so check it when behavior gets weird.

    01

    How an LLM actually thinks

    Goal: understand tokens, prediction, context and temperature well enough that the rest of the lesson makes sense.

    It's autocomplete, scaled up enormously

    A large language model (LLM) does one thing. It looks at some text and predicts what piece of text comes next. Then it adds that piece to the end and predicts again, over and over. That's the whole engine. Chatting, coding and "reasoning" are all built from that one move repeated thousands of times.

    The pieces it predicts are called tokens. A token is usually a word or a chunk of a word. In English, one token averages about three quarters of a word, so 1,000 tokens is roughly 750 words.

    Token splitterLab 1.1
    Words: 0Tokens (approx.): 0Tokens per word: 0

    This is a simplified splitter. Real tokenizers differ from model to model, but they work the same way: common words get one token, rare or long words get split, and punctuation and spaces count too.

    How a model gets made

    1. Pretraining. The model reads a huge amount of text and learns to predict the next token. Afterwards it knows a lot, but it's only a raw autocomplete. Ask it a question and it might continue with five more questions.
    2. Instruction tuning. It trains on thousands of example conversations, so it learns the pattern "user asks, assistant answers helpfully." Models labeled Instruct or Chat have had this step.
    3. Preference and safety tuning. People and other models rate its answers, and it's nudged toward the better ones. This step shapes its tone, its honesty about uncertainty, and when it refuses. An abliterated model has had the refusal part of this step surgically removed. Module 3 covers what that means for you.

    Parameters: the model's knobs

    A model's knowledge is stored in billions of numbers called parameters (or weights). "8B" means 8 billion of them. More parameters usually means more knowledge and better reasoning, but it also means more memory needed and slower answers. That trade-off is the main challenge of running AI at home.

    Context window: its entire short-term memory

    The context window is the most text the model can look at in one go, measured in tokens. Everything has to fit inside it: the system prompt, the whole chat history, any tool descriptions, any files you paste, and the answer it's writing.

    Key idea

    The model has no memory between messages. Every time you send a message, the chat app sends the entire conversation so far back to the model. When the conversation gets longer than the context window, the oldest parts get cut off, and the model "forgets" them. That's why your local bot might forget what you said 20 messages ago.

    Temperature: how adventurous it is

    For each next token, the model scores every possible option. Temperature controls how it chooses among them. Low temperature almost always picks the top option, which makes it predictable and focused. High temperature spreads the chances out, which makes it more creative but also more likely to say something random or wrong.

    Next-token predictorLab 1.2

    The model has read: My favorite food is

    Picks will show up here.

    Try 0.2, then 1.8. At 0.2 you get "pizza" nearly every time. At 1.8, even "cardboard" starts showing up. Rule of thumb: 0.2 to 0.4 for facts and code, about 0.7 for normal chat, 0.9 to 1.1 for creative writing.

    Why it makes things up

    The model predicts plausible text, not true text. If it doesn't know a fact, the most plausible-sounding continuation is often a confident, made-up answer. This is called hallucination. Small models do it more than big ones, and every model does it sometimes. Always double-check facts that matter.

    02

    Your PC vs. the model

    Goal: know exactly which models your computer can run well, and why some are fast and others crawl.

    Why your local model isn't Claude

    Frontier models like Claude run on racks of data-center GPUs with hundreds of gigabytes of very fast memory. They're believed to be many times larger than anything that fits on a home PC, and they're trained with far more compute. An 8B model on your machine can be genuinely useful, but it will be weaker at hard reasoning, long instructions, niche facts and multi-step tool use. That's normal. You haven't set it up wrong.

    Quantization: compressing the brain

    Out of the box, each parameter is stored as a 16-bit number, so an 8B model would need about 16 GB just to load. Quantization rounds those numbers to fewer bits, the way a JPEG compresses a photo. The model files you download in LM Studio are GGUF files, and the quantization level is in the name:

    QuantBits per weight8B model sizeQuality
    Q8_0~8.5~8.5 GBAlmost the same as the original
    Q6_K~6.6~6.6 GBVery close
    Q5_K_M~5.7~5.7 GBGreat, with a tiny loss
    Q4_K_M~4.9~4.9 GBBest balance for most people
    Q3_K_M~3.9~3.9 GBNoticeably dumber
    Q2_K~3.0~3.0 GBOften broken or rambling

    A useful rule: a bigger model at Q4 usually beats a smaller model at Q8, as long as it fits.

    Hardware vs. model size cheat sheet

    Quick formula at Q4_K_M: GB needed ≈ billions of parameters × 0.6, plus 1 to 2 GB for context. So an 8B model needs about 8 × 0.6 + 1.5 ≈ 6.3 GB.

    System RAM matters too. When a model doesn't fit in VRAM, the rest has to fit in RAM, and Windows plus your apps already use 4 to 6 GB of your 16.

    Why speed is about memory, not the processor

    To produce every single token, the computer has to read through the whole model once. So speed is mostly limited by how fast memory can be read, which is called memory bandwidth:

    • Your graphics card's VRAM reads at roughly 220 to 450 GB/s, depending on the card.
    • Your system RAM (DDR4, two sticks) reads at roughly 35 to 45 GB/s. With only one stick, it's half that.

    So a model that fits entirely in VRAM is around 5 to 10 times faster than one running from system RAM. When a model is too big for VRAM, LM Studio splits it, putting some layers on the GPU and the rest on the CPU. This is called offloading. The slow CPU part then drags down the speed of the whole thing.

    The context window also takes up memory. Its memory, called the KV cache, grows with every token of context. That's why turning the context length up to 32k can push a model that fit before out of VRAM.

    Why it's slow only sometimes

    A model has two speeds, and your RX 580 is very different at each:

    • Reading speed (prompt processing). Before it writes a single word, the model has to read everything in its context: system prompt, tool descriptions, chat history and your new message. This needs raw computing power, and the RX 580 is an older card that only runs through Vulkan. It reads roughly 150 to 250 tokens per second on an 8B model.
    • Writing speed (generation). This depends on memory bandwidth, and the RX 580's 256 GB/s is decent. You get about 20 to 28 tokens per second once it starts.

    So "slow sometimes" usually means it's stuck reading. Common triggers:

    AMD-specific tips
    • Use the Vulkan runtime in LM Studio. In LM Studio's runtime settings, choose the Vulkan version of llama.cpp. Your RX 580 isn't supported by AMD's ROCm on Windows, so Vulkan is your only GPU option. If the runtime is set to CPU, everything runs on the processor.
    • Keep your AMD drivers up to date. Vulkan performance on older cards improves with newer drivers and LM Studio updates.
    • Move the GPU offload slider all the way up when the model fits. If it's at zero, everything runs on your CPU.
    • Check that it's actually on the GPU. Open Task Manager, go to Performance, then GPU, and watch "Dedicated GPU memory" jump when the model loads.
    • Your Ryzen 5 2600 has no built-in graphics, so the same 8 GB card also runs your display. Chrome, Discord and games all use some VRAM. Close them when you want the most speed.
    • Set CPU threads to 6, one per physical core. More threads often doesn't help.
    03

    Make it act like a real chatbot

    Goal: fix the settings that make local models act weird, and understand what your abliterated model can and can't do.

    What makes a chatbot feel "good"

    When you talk to Claude, several layers work together. Most of them aren't the model itself:

    1. A careful system prompt. These are hidden instructions about tone, format and behavior. You control this.
    2. The correct chat template. This is the special formatting that marks where the user's turn ends and the assistant's begins. You control this.
    3. Sensible sampling settings, such as temperature. You control this.
    4. Enough context so it remembers the conversation. You control this, within your memory limits.
    5. Tools like web search, file reading and code running. You can add these (Module 5).
    6. A huge, carefully trained model. This is the part you can't copy at home.

    You control five of the six. Get those right and an 8B model feels far better.

    Settings to start with

    Top P0.9Ignores the long tail of unlikely tokens.

    The truth about abliterated models

    Researchers found that a model's tendency to refuse is mostly controlled by one specific "direction" inside its internal math. Abliteration finds that direction and subtracts it from the weights. The result is a model that almost never says "I can't help with that."

    What abliteration doesWhat it doesn't do
    Removes most refusalsMake the model smarter or more knowledgeable
    Makes it answer anythingMake its answers more accurate. It will confidently answer things it doesn't know.
    Changes the weights slightlyCome for free. Many abliterated models lose a bit of quality, coherence or tool-calling skill.
    You are the safety layer now

    With the filters gone, it's on you to judge the output. Treat medical, legal, chemical or "how to" safety information from it as unreliable. It will produce plausible, dangerous nonsense as calmly as it produces facts. Don't post its output as truth without checking it.

    For your goal of a regular, helpful chatbot, the normal Instruct version of the same model often behaves better: it's more honest about uncertainty and better at following instructions. Keep both and compare them using the same prompts.

    Build your system prompt

    The system prompt is the single biggest lever you have. For small models, keep it short and clear. Under about 150 words works better than a page of rules, because small models lose track of long instruction lists.

    Ten techniques that work
    
  
      
    
    1. Be specific. Vague in, vague out. Name the audience, length and purpose.
      2. 
    
    2. Explain why. "Keep it short because I'll read it on my phone" works better than "keep it short," because the model can apply the reason to cases you didn't think of.
      3. 
    
    3. Show examples (few-shot prompting). Give two or three examples of the input and output you want. This is the most powerful technique for small local models.
      4. 
    
    4. Ask for a format. Tables, bullet points, JSON, "exactly 3 options." It's easier to read, and much easier for code to use.
      5. 
    
    5. Break big jobs into steps (prompt chaining). Outline first, then draft each section, then edit. Small models fail at "do everything at once."
      6. 
    
    6. Let it think first. "Work through it step by step, then give the final answer on its own line." Reasoning models like Qwen3 do this on their own.
      7. 
    
    7. Separate instructions from data. Wrap pasted text in markers like <article> ... </article> or ### so the model doesn't confuse your article with your instructions.
      8. 
    
    8. Give it permission to not know. "If you're not sure, say so." This noticeably reduces made-up answers.
      9. 
    
    9. Iterate. Treat the first answer as a draft. "Shorter." "More examples." "Less formal." It's a conversation.
      10. 
    
    10. Put the important part last in long prompts. With lots of pasted text, put your actual question at the end, after the material.

      05
      Tools and agents
      
  
      Goal: understand how a model "uses" a tool, why more tools can make things worse, and write your first tool-using program.
      

  
      
    Why the bare model felt way worse than agents
    
      You started with agents and then switched to just the model, and it felt much worse. That's expected. An agent app like Claude Code runs a huge cloud model and wraps it in a long, carefully written system prompt, a set of tools, skills, and code that manages its memory. The bare chat in LM Studio has none of that, and it runs a much smaller model.
      
    
      You were comparing a whole workshop to a single tool. This module and the next rebuild the workshop one piece at a time, so you can see what each piece adds.
      
  
      

  
      A model can't actually do anything
      
  
      A model only outputs text. It can't browse, run code or check the time. "Tool use" is a trick: you describe some tools to the model, and when it wants one, it outputs a specially formatted request. Your program sees the request, runs the real function, and sends the result back as another message. The model then continues with the new information.

      Why more tools isn't better
      
  
      You figured this out the hard way already. Here's why it happens:
      
  
        
    
      • Every tool costs context. Each tool's name, description and parameters are sent with every message. Twenty tools can take thousands of tokens of your 8k window before you've typed anything.
        • 
    
      • Choices cause confusion. When tools overlap (like search_web, browse and fetch_url), the model has to guess which one to use, and it often guesses wrong or calls several.
        • 
    
      • Small models suffer most. An 8B model is reasonable with 2 to 4 clear tools. With 15, it starts making up tool names and passing bad arguments.

      • Each tool does one clear job, and no two tools do the same job.

      MCP: plug-in tools
      
  
      The Model Context Protocol (MCP) is a standard way to package tools so any AI app can use them. Think of it as USB-C for AI tools. LM Studio can load MCP servers, and coding agents use them heavily. Watch out: one MCP server can add 10 or 20 tools at once. That's how you ended up with too many. Turn on only the servers you need for the current task.
      

  
      Agents: tools in a loop
      
  
      An agent is a model plus tools plus a loop plus a goal. It keeps calling tools, reading results and deciding the next step until it decides it's done. Coding agents work this way: read files, edit, run tests, read errors, edit again.
      
  
      The problem is that mistakes compound. If each step has a small chance of going wrong, a long task adds up all those chances.
      
  
      
    
      Why long agent tasks failLab 5.3
      
    
      
      
      
      
      
    
      
    
      
      
      Chance the whole task succeeds0
      
      
      Same task broken into 4 checked chunks0
      
    
      
    
      
  
      
  
      This is why big models are much better agents. Going from 95% to 99% per step turns a 36% success rate on 20 steps into 82%. It's also why the fix for agents is short tasks you check, not more tools.

      Step 1: a chatbot with memory
      
  
      This shows the key idea from Module 1. The program keeps the conversation in a list and sends all of it every time.
      
  
      chat.py
      

      from openai import OpenAI

client = OpenAI(base_url="http://localhost:1234/v1", api_key="lm-studio")
MODEL = "paste-your-model-identifier-here"

# The whole conversation lives here. This list IS the bot's memory.
messages = [{"role": "system", "content": "You are Nova, a friendly, concise assistant."}]

while True:
    user = input("you> ")
    if user.lower() in ("quit", "exit"):
        break
    messages.append({"role": "user", "content": user})

    reply = client.chat.completions.create(model=MODEL, messages=messages, temperature=0.7)
    text = reply.choices[0].message.content
    print("nova>", text)

    # Save the answer so the model "remembers" it next turn.
    messages.append({"role": "assistant", "content": text})

      Step 2: add two tools
      
  
      The model asks for a tool, your code runs it, and the result goes back. It's the same loop as Lab 5.1, written in code. For this, use a model that supports tool calling, like Qwen3 or Llama 3.1 Instruct. Abliterated versions are sometimes worse at it.
      
  
      tools.py
      

      import json, datetime
from openai import OpenAI

client = OpenAI(base_url="http://localhost:1234/v1", api_key="lm-studio")
MODEL = "paste-your-model-identifier-here"

# 1. The real functions. The model never runs these; your code does.
def percent_of(percent, number):
    return round(number * percent / 100, 2)

def get_time():
    return datetime.datetime.now().strftime("%A %I:%M %p")

FUNCTIONS = {"percent_of": percent_of, "get_time": get_time}

# 2. Descriptions the model reads. Clear names, and say WHEN to use each.
TOOLS = [
    {"type": "function", "function": {
        "name": "percent_of",
        "description": "Calculate a percentage of a number. Use for tips, discounts and tax.",
        "parameters": {"type": "object",
            "properties": {"percent": {"type": "number"}, "number": {"type": "number"}},
            "required": ["percent", "number"]}}},
    {"type": "function", "function": {
        "name": "get_time",
        "description": "Get the current local day and time.",
        "parameters": {"type": "object", "properties": {}}}},
]

messages = [
    {"role": "system", "content": "You are a helpful assistant. Use a tool when it gives a more accurate answer."},
    {"role": "user", "content": "What's an 18% tip on $47.50, and what day is it?"},
]

# 3. The loop. Stop after 5 rounds so a confused model can't loop forever.
for _ in range(5):
    response = client.chat.completions.create(model=MODEL, messages=messages, tools=TOOLS)
    msg = response.choices[0].message

    if not msg.tool_calls:          # no tool requested, so this is the final answer
        print(msg.content)
        break

    messages.append(msg.model_dump(exclude_none=True))   # remember what it asked for
    for call in msg.tool_calls:
        args = json.loads(call.function.arguments or "{}")
        result = FUNCTIONS[call.function.name](**args)
        print(f"[tool] {call.function.name}({args}) -> {result}")
        messages.append({"role": "tool", "tool_call_id": call.id, "content": str(result)})
      
  
      
    Explain this code in plain English
    
        
      
      1. The real functions (def percent_of, def get_time) are ordinary Python. def means "define a function." The model can't run these. Only your program can.
        2. 
      
      2. FUNCTIONS is a lookup table from a tool's name to the real function, so the program can find the right one when the model asks for it by name.
        3. 
      
      3. TOOLS is the menu the model reads: each tool's name, a description of when to use it, and what inputs it needs. This text is a prompt. Write it carefully (Module 6).
        4. 
      
      4. messages starts the conversation with a system prompt and a question.
        5. 
      
      5. The loop (for _ in range(5)) runs at most 5 rounds. Each round it sends everything to the model.
        
          
          
        • If the model answered normally (no tool_calls), print the answer and stop.
          • 
          
        • If it asked for tools, save its request, run each requested function with the arguments it gave, print what happened, and add each result as a tool message. Then go around again so the model can use the results.
          • 
        
        
      
        6. 
    
      
    
      The [tool] lines it prints let you watch the model's decisions. That's the best way to learn how good or bad your model is at using tools.
      
  
      
  
      Challenges: (1) Add a third tool, roll_dice(sides). (2) Ask something that needs no tool and check that it doesn't call one. (3) Try the same script with your abliterated model and a normal one, and compare how reliably each calls the tools.
      

  
      
  
      

      



      
  
      06
      How it all fits together
      
  
      Goal: see how system prompts, skills, tools and MCP all share one context window, how they get in each other's way, and how much a tool can really help a small, low-context model.
      

  
      Four ways to give a model more abilities
      
  
      
    
      PieceWhat it isWhen it uses contextExample
      
    
      
      System promptAlways-on instructions about who the bot is and how it behavesEvery message, all of it"You are Nova, a concise helper."
      
      
      SkillA saved set of instructions (sometimes with example files or scripts) for one kind of task, loaded only when neededA one-line description every message. The full text only when it's used."How to make study flashcards in my format"
      
      
      ToolA function the model can ask your program to runIts description every message, plus its result whenever it's calledCalculator, web search, read_file
      
      
      MCP serverA ready-made bundle of tools in a standard packageEvery tool in the bundle, every messageA GitHub server that adds 20 tools at once
      
          
  
      
  
      
    Kitchen analogy
    
      The context window is your counter space. The system prompt is the house rules taped to the wall. Skills are recipe books on a shelf: you read the spines, and you only open the one you're cooking from. Tools are appliances, and every one you plug in takes counter space. An MCP server is a whole appliance kit plugged in at once. A small model has a small counter.
      
  
      

  
      How skills work
      
  
      Skills are a feature of apps like Claude Code and the Claude apps. They use a trick called progressive disclosure, which means showing a little at first and loading more only when it's needed:
      
  
        
    
      1. At the start, the model sees only each skill's name and a one-line description, about 50 to 100 tokens each.
        2. 
    
      2. You ask for something that matches a description, like "make flashcards from my notes."
        3. 
    
      3. The full skill loads into context. That's its instructions, format rules and examples, often 1,000 to 5,000 tokens.
        4. 
    
      4. The model follows it, sometimes running scripts that come with the skill through its tools.
        5. 
  
      
  
      So 20 installed skills might cost only about 1,500 tokens until one is used, while 20 tools cost their full descriptions on every single message. A skill is really just a saved, well-written prompt. That's why prompting is the core skill underneath all of this.
      
  
      LM Studio doesn't have skills, but you can do the same thing yourself. Keep a folder of prompt files (flashcards.txt, essay-feedback.txt) and paste in the one you need, or have your Python program load the right file. On an 8k model, watch the size: a 4,000-token skill uses half your context.
      

  
      One request, every piece working together
      
  
      Say you ask an agent: Make 10 flashcards from biology.txt. Here's what goes on:
      
  
        
    
      1. System prompt (always there): "You are a study helper..."
        2. 
    
      2. Skill descriptions (always there): the model notices "flashcards: makes study cards in the user's format" matches, so the full flashcard skill loads.
        3. 
    
      3. Tool descriptions (always there): the model sees it has read_file and calls it with biology.txt.
        4. 
    
      4. Tool result: the file's text comes back. This is often the biggest thing in the whole context.
        5. 
    
      5. Answer: the model writes the cards using the notes, in the format the skill described.
        6. 
  
      
  
      All five layers sit in the same context window at the same time. On a 200k cloud model, that's no problem. On your 8k model, it can easily overflow.

      How the pieces get in each other's way
      
  
      
    
      ProblemWhat you'll seeFix
      
    
      
      CrowdingThe bot forgets the chat sooner and takes longer before it starts answeringTurn off tools, skills and MCP servers you don't need for this task.
      
      
      Conflicting instructionsThe system prompt says "keep it short," a skill says "write a detailed report," and the model randomly follows one or mixes themKeep one source of truth, or say which wins: "When a skill gives a format, follow it over the length rule."
      
      
      Overlapping toolsIt picks the wrong tool or calls two that do the same thingOne tool per job (Lab 5.2).
      
      
      FloodingAfter a web search, it ignores your rules and rambles about the pageMake tools return short, trimmed results. A huge result buries your instructions.
      
      
      Lost in the middleRules in the middle of a long context get ignoredKeep the system prompt short. Repeat the most important rule right next to your question.
      
      
      Tool-happyIt calls tools for things it already knows, like "what's 2 + 2"Say in the description when not to use it: "Only for numbers with decimals or more than 2 digits."
      
      
      Prompt driftThe bot slowly forgets its personality in long chatsThat's the history pushing out older content. Start new chats, or summarize and restart.
      
          
  
      

  
      Tool descriptions are prompts too
      
  
      The model decides which tool to use only from the name and description you write. So writing tools is prompting, and everything from Module 4 applies. Small models need this spelled out even more.
      
  
      
    
      
      
      Weaksearch: "Searches stuff."
      
      
      Strongsearch_my_notes: "Search the user's class notes by keyword. Use when the user asks about something from their classes. Returns the 3 best-matching paragraphs."
      
      
      The name says what is searched. The description says when to use it and what comes back, so the model knows what to expect.
      
    
      
    
      
      
      WeakSystem prompt: "You have tools."
      
      
      StrongSystem prompt: "Use percent_of for any percentage math. Use get_time for questions about today's date or time. For everything else, answer directly without tools."
      
      
      Small models do much better when the system prompt maps situations to tools in plain words.
      
    
      
  
      

  
      How much can a tool help a small, low-context model?
      
  
      Tools fix what the model doesn't have: facts, precision, fresh information and memory. They can't fix what the model can't do: deep reasoning and long planning. Pick a task to see the difference.

    Main takeaway
    
      For a low-context model, the best tool is one that acts as external memory. A search tool that returns only the 3 most relevant paragraphs lets an 8k model answer questions about a 300-page textbook that would never fit in its context. That's the biggest upgrade a tool can give you. Keep it to 1 to 3 tools that return short results, and the tools add more than they cost.

      Your build plan
      
  
      Goal: a repeatable way to build lots of AI projects, plus ideas that fit your hardware.
      

  
      The workflow for every project
      
  
        
    
      1. Prototype the prompt in a chat app. Get the behavior right by hand before writing any code.
        2. 
    
      2. Write 10 test inputs. Include easy, hard and weird cases. This is called an eval. It's how you'll know if a change actually helped.
        3. 
    
      3. Move it into code (Module 5, step 1). Lock in the system prompt.
        4. 
    
      4. Try it local. Run your 10 tests on your 8B model. If it passes, it's free and private. If it fails, try a better prompt, a bigger model or a cloud model.
        5. 
    
      5. Add tools one at a time. Re-run your tests after each one. If a tool makes the results worse, remove it.
        6. 
    
      6. Keep notes on what worked: model, quant, settings, prompt. Future you will thank you.

      Glossary
      
  
      
    
      Token
      A chunk of text the model reads and writes, about three quarters of a word.
      
    
      Parameters
      The billions of numbers that store what a model learned. "8B" means 8 billion.
      
    
      Context window
      The most tokens a model can consider at once, including the chat history, system prompt, tools and its own answer.
      
    
      Inference
      Running a trained model to get answers (as opposed to training it).
      
    
      Quantization
      Storing weights with fewer bits so the model fits in less memory, at a small cost in quality.
      
    
      GGUF
      The model file format used by LM Studio, Ollama and llama.cpp.
      
    
      VRAM
      Your graphics card's memory. It's fast, and the model should live there when possible.
      
    
      Offloading
      Splitting a model's layers between the GPU and CPU when it doesn't fit in VRAM.
      
    
      KV cache
      Memory that holds the model's working state for every token in the context. It grows with context length.
      
    
      Temperature
      How random the token choices are. Low means focused, high means creative or chaotic.
      
    
      System prompt
      Hidden instructions that set the bot's behavior for the whole chat.
      
    
      Chat template
      The special formatting that marks user and assistant turns. If it's wrong, the bot gets weird.
      
    
      Instruct model
      A model trained to follow instructions and chat, not just autocomplete.
      
    
      Abliterated
      A model with its refusal behavior removed from the weights. It's not smarter, just unfiltered.
      
    
      Hallucination
      When a model states something false with confidence.
      
    
      Few-shot prompting
      Including a few examples in the prompt to show the pattern you want.
      
    
      Tool call
      A structured request from the model asking your program to run a function.
      
    
      Skill
      A saved package of instructions (and sometimes files or scripts) for one kind of task. Only a short description is loaded until it's needed.
      
    
      Progressive disclosure
      Showing the model a short summary first and loading the full details only when they're needed. It saves context.
      
    
      Prompt processing
      The model reading everything in its context before it writes. This is the RX 580's slow part.
      
    
      Lost in the middle
      Models pay less attention to information buried in the middle of a long context.
      
    
      MCP
      Model Context Protocol, a standard way to package tools so any AI app can use them.
      
    
      Agent
      A model plus tools in a loop, working toward a goal over many steps.
      
    
      RAG
      Retrieval-augmented generation: finding relevant text and adding it to the prompt so the model can use it.
      
    
      MoE
      Mixture of experts, a model that uses only part of its parameters for each token, so it's faster than its size suggests.
      
    
      Eval
      A fixed set of test inputs you use to measure whether a change made your AI better or worse.
